# Airwallex Transaction RFI contract (as documented, 2 Nov 2026)

Carnet is built on the behaviour below. Items that were unknown at planning time were resolved by the M0 live sandbox spikes
(`fixtures/airwallex/`) and are marked **OBSERVED** with the fixture and date (3 Nov 2026). Sources: Airwallex developer docs
(`airwallex.com/docs/...`, pages fetched 2 Nov 2026) and the Airwallex docs MCP.

## RFI object and endpoints
- `GET /api/v1/rfis` (filters `statuses`, `types`, `from_created_at`, `end_created_at`, `page`, `page_size`), `GET /api/v1/rfis/{id}`, `POST /api/v1/rfis/{id}/respond`.
- Statuses `ACTION_REQUIRED`, `ANSWERED`, `CLOSED`. Types include `TRANSACTION`. An RFI has an `active_request` with `expires_at`; expiry moves the RFI to `CLOSED`.
- A question has `id`, `title{en,zh}`, `description`, `comment`, `answer{type}` and `sources[{id,type}]`. Transaction sources: `CHARGE`, `CONNECTED_ACCOUNT_TRANSFER`, `DIRECT_DEBIT`, `DEPOSIT`, `TRANSFER`.
- Answer types `TEXT`, `ATTACHMENT`, `IDENTITY_DOCUMENT`, `CONFIRMATION`, `LIVENESS`, `ADDRESS`.
- Respond body: `{questions:[{id, answer:{type, text | attachments:[{file_id}] | confirmed | address | identity_document, comment}}]}`. **OBSERVED:** a partial response (one of two questions, TEXT only or ATTACHMENT only) is rejected: 400 `invalid_argument`, "Please answer all questions in the request", RFI stays `ACTION_REQUIRED` (`rfi-check2-respond-partial-text`, `rfi-check2-respond-partial-attachment`). Answering all questions returns 200 and the RFI becomes `ANSWERED` (`rfi-check2-respond-full`). A second respond on an `ANSWERED` or `CLOSED` RFI returns 400 `invalid_state_for_operation` (`rfi-check2-respond-again-after-answered`, `rfi-check5-respond-after-close`). Responding is only valid in `ACTION_REQUIRED`.
- Webhooks `rfi.action_required`, `rfi.answered`, `rfi.closed` carry only `data.id` (the RFI id); the RFI must be fetched.

## Sandbox simulation
- `POST /api/v1/simulation/rfis/create` `{type, questions?[{answer.type, title{en}, description{en}, sources[]}]}`. "All RFIs for specified type must be in CLOSED status": **one open Transaction RFI at a time** per account.
- `POST /api/v1/simulation/rfis/{id}/follow_up` reopens answered questions by id and/or appends new ones; `POST /api/v1/simulation/rfis/{id}/close`.
- `x-on-behalf-of` is documented for platform accounts only. **OBSERVED:** a plain sandbox account creates simulated `TRANSACTION` RFIs without it (`rfi-check1-create`, 3 Nov 2026). With a `TRANSFER` source the transfer must already be `PROCESSING`; right after creation (`SCHEDULED`) the same call returns 400 `invalid_argument` "Invalid source" (`rfi-check1-create-while-scheduled`). The sources of a simulated RFI are set per question; an RFI created with no sources gets a synthetic `DEPOSIT` source `SIMULATION_<uuid>` (`rfi-check7-create-no-sources`), so a true orphan is not reproducible.
- **OBSERVED one-open rule:** a second create for the same type and source while one is open returns 400 `invalid_state_for_operation` "There is an active RFI for the same type and source. Please close the existing RFI before creating a new one." (`rfi-oneopen-second-create-while-open`). RFIs for a different source, or with none, can be open at the same time (`rfi-check7-create-other-source-while-open`), so the rule is per type and source, not per account.
- **OBSERVED follow_up:** `POST /api/v1/simulation/rfis/{id}/follow_up` needs `{questions:[...]}`; an entry with only `id` reopens that answered question, an entry with `title`, `description`, `answer`, `sources` appends a new one (a repeated title was accepted). The RFI returns to `ACTION_REQUIRED` with all questions in `active_request` and the earlier round in `answered_requests` (`rfi-followup-reopen-and-append`, `rfi-followup-fetch`, `rfi-followup-respond-all`).
- **OBSERVED close:** `POST /api/v1/simulation/rfis/{id}/close` works on `ACTION_REQUIRED` and `ANSWERED` RFIs and returns the RFI with status `CLOSED`; closing a closed RFI returns 400 `invalid_state_for_operation` "rfi session status is illegal" (`rfi-check5-close-open`, `rfi-check5-close-again`, `rfi-check5-close-answered`).
- **OBSERVED sources:** the created and the fetched RFI carry `sources` on each question (`rfi-check7-fetch-multi`); a question with two sources kept only the first (`rfi-check7-create-multi-source`); different sources per question work (`rfi-check7-create-per-question-sources`). The webhook payload is pending M0-05.

## Transfers and RFIs
- An RFI does not add a transfer status. Transfer statuses (API version 2025-06-30 and later): `IN_APPROVAL`, `APPROVAL_RECALLED`, `APPROVAL_REJECTED`, `APPROVAL_BLOCKED`, `SCHEDULED`, `OVERDUE`, `PROCESSING`, `SENT`, `PAID`, `FAILED`, `CANCELLED`. An RFI may arrive while a transfer is `SCHEDULED`, `PROCESSING` or `SENT`.
- Answering or closing an RFI does not move the transfer: "Responding to or closing an RFI does not by itself send the transfer … the transfer outcome is decided by the review and may be `SENT` or `FAILED`." Carnet therefore derives payment status from the transfer, never from the RFI.
- **OBSERVED held funds:** creating a transfer debits `amount_payer_pays` from `available_amount` at once (USD 9998041 to 9997998 for a 40 USD transfer with a 3 USD fee); `pending_amount` and `reserved_amount` stay 0 before, during and after an open RFI, and the transfer keeps `funding.status` `FUNDED` (`rfi-check8-balances-after-create`, `rfi-check8-balances-rfi-open`, `rfi-check8-transfer-rfi-open`). Held funds are therefore not shown as a separate amount; Carnet keeps treating a held transfer's funds as unavailable, which the balance already reflects.

## Files
- `POST https://files.sandbox.airwallex.com/api/v1/files/upload` multipart `file` (filename ≤ 50 characters), documented 20 MB maximum, returns `file_id` used in `answer.attachments[].file_id`. **OBSERVED:** PNG, JPEG and PDF were accepted by upload and by respond (`rfi-check3-upload-png`, `-pdf`, `-jpeg`, `rfi-check3-respond-*`). The upload endpoint lists the allowed extensions: pdf, jpg, png, doc, docx, xls, xlsx, csv, jpeg, cer, bmp, tif, tiff, webm, mov, mp4, heic, m4a, weba, mp3, wav, aac, amr, xml; a `.txt` upload returns 400 `invalid_file_extension` (`rfi-check3-upload-txt`). A 22,020,096 byte file (over 20 MB) was accepted by upload and by respond (`rfi-check3-upload-oversized-21mb-pdf`), so the documented limit is not enforced in the sandbox; Carnet enforces its own limit. Carnet always uploads PDF or JPEG.
- **OBSERVED TEXT length:** answers of 1,000 up to 20,000,000 characters were accepted; no rejection was found, so there is no usable limit to cite (`rfi-check6-summary`). Carnet caps its own answers.
- **OBSERVED transfers and RFIs:** with an RFI open the transfer moved `SENT` then `PAID` and `SENT` then `FAILED` (fetched `CANCELLED`) normally, and the RFI stayed `ACTION_REQUIRED` (`rfi-check4-summary`). Closing or answering the RFI left the transfer `PROCESSING` (`rfi-check5-summary`). The simulator occasionally returns 500 on a transition whose effect was applied; read the transfer instead of trusting the response.

## Webhooks
- Signature: `HMAC_SHA256(secret, x-timestamp + rawBody)`, hex, compared with `x-signature`. Delivery is at-least-once and unordered, retried with exponential backoff for about three days. Subscriptions are created in the web app only.

## Limits
- Sandbox (documented): 20 requests/second globally, 10 per endpoint, 10 concurrent; token lifetime 30 minutes; `request_id` unique for 7 days.
- Observed in M0-03 (`docs/evidence/airwallex-money-path.md`): 150 parallel balance reads in 1.3 s returned no 429; reusing a transfer `request_id` returns 400 `duplicate_request_id` with the existing transfer id in `details.id`; a simulated `FAILED` transfer is fetched as `CANCELLED` with a nested `failure` object.
